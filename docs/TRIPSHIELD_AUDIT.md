### Security and delivery review

- **Authentication:** Passwords are bcrypt-hashed (`AuthController.java:16,29,38`). Registration checks 8–72 UTF-8 bytes. Login returns a generic 401 for bad credentials. Sessions use 32 random bytes, store only SHA-256 hashes, expire after 12 hours, and are deleted on logout/expired access (`Access.java:25-59`). Rate limiting, account disabling, forced revocation, and coordinator credential rotation are absent. These are hardening gaps for public deployment, not failures in the tested college-demo paths.
- **Invitations and authorization:** Coordinators alone issue codes; the database stores code hashes, a seven-day expiry, and a used timestamp. Claim requires an authenticated account with the invited email and an unowned active trip. Trip access checks `ownerUserId`; coordinator mutations check role and lock the trip row. The API tests exercised cross-user denial. Invitation delivery is manual, so secure private sharing is an operational requirement. Existing guest trips do not become visible merely through registration.
- **Outbox:** The check-in writes an outbox row in its database transaction. `OutboxClaims` locks and leases a due row in a separate transaction; `EmailAlerts` performs the SMTP call after that claim transaction completes, then records success or schedules backoff. A mocked failure and a mocked success passed. Crash/slow-send duplicate delivery remains possible, and no live SMTP reliability test was performed.

### Safety incident during browser setup

**Verified incident:** At 23:27 local time, a `spring-boot:run` launch with the `test` profile unexpectedly loaded ignored `backend/config/local.properties`, connected to `jdbc:mysql://localhost:3306/tripshield`, and Flyway baselined that existing development schema at V1 and applied the additive V2 migration. The startup log reported both actions and a successful application start on port 18080. The server was stopped immediately. No browser action, test cleanup, reset, drop, or application API request was sent to that server. V2 adds columns, indexes, and new tables; it contains no `DELETE` or `DROP`, but **development-row preservation was not measured before and after**, so that claim is not verified. The migration must be treated as a change to the development schema, contrary to the intended test-only safety boundary. Do not roll it back blindly.

**Containment:** `backend/src/main/resources/application.properties:1-4` no longer imports local credentials or supplies a default datasource. Local credentials are imported only under the explicit `local` profile (`application-local.properties:1-6`). `BackendApplication.java:11-21` now rejects a `test`-profile launch unless the URL and user exactly match the isolated test schema before Flyway initializes. A repeat launch without explicit test datasource variables failed at this guard, before a database connection. A subsequent launch with restricted `tripshield_test_app` overrides logged `jdbc:mysql://127.0.0.1:3306/tripshield_test`, schema version 2, and HTTP port 18080. Both temporary servers were stopped. This confirms the guard on the Maven launch path; other bootstrapping paths still need review.

## Executive summary

TripShield is a functional prototype with a substantial set of planning and recovery workflows. Phase 2 fixed the reproduced Duffel offset timestamp parse failure, rejects repeated cancellation, and added row-locked state changes. The latest complete backend suite passed 29 tests (17 database-backed integration tests); frontend tests, lint, and build also passed. Duffel and SMTP were mocked. ## Security and data review

- Password hashes use BCrypt; session bearer tokens are random and only SHA-256 hashes are stored (`AuthController.java`, `Access.java`, `AppSession.java`). The frontend stores the bearer token in `sessionStorage` (`frontend/src/services/api.ts`), so an XSS flaw would expose it; no cookies/CSRF mechanism is used.
- Role authorization is implemented manually at controller calls. Review coverage is incomplete; no systematic endpoint matrix or security filter is present.
- Ownership is email-based rather than a stable foreign key. Because traveler registration is open and unverified, email equality is not proof of identity for guest trip access (A-01).
- Entities use public mutable fields and few database constraints beyond primary keys, unique user email, and unique session hash. Trip/item status, string lengths, alternative references, and actor references lack explicit constraints/indexes (`Trip.java`, `TripItem.java`, `Alternative.java`, `TripEvent.java`). Hibernate `ddl-auto=update` is enabled in `application.properties:3-7`; this is convenient for prototypes but not a controlled production migration strategy.
- `TripController.list` fetches all trips, filters in application memory, and invokes session/user lookup for each trip (A-05). Add query-level authorization and pagination.
- No production application source was changed during this phase. No real credential, token, or local properties content is included in this report.
